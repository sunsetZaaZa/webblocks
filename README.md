# Webblocks

React, TypeScript and Vite website editor and presentation framework.

**Framework preview 0.1.6.**

## Local development

Use Bun 1.4.5, pinned in `.bun-version` and `package.json`. No separate Node.js or npm installation is required for the application build. `bun.lock` is the only dependency lockfile. Keep the supplied audited lockfile unchanged; do not run automatic upgrades or bypass qualification failures. When overlaying this source archive onto an older checkout, remove the obsolete `package-lock.json` and `.nvmrc` explicitly (for example, `rm -f -- package-lock.json .nvmrc` from the project root). Keep `bun.lock` and `.bun-version`.

```sh
bun install --frozen-lockfile
bun run dev
```

The default development URL is `http://localhost:5173/`. `VITE_APP_PORT` can override the port.

## Validation and build

```sh
bun run test:baseline
bun run lint
bun run test:unit
bun run build
bun run preview
```

`test:baseline` runs using only Bun and checks static image and font references, lockfile metadata, Storybook scaffolding and fixture model compatibility. `bun run test` runs baseline checks and Vitest unit tests. `dist/` is generated by the production build; it must not be checked into Git.

## Storybook and browser tests

```sh
bun run pw:install chromium firefox webkit
bun run storybook
bun run build-storybook
bun run test:storybook
bun run test:storybook-static
bun run test:all
```

Storybook uses an independent Vite configuration, memory-only Redux fixtures, and MemoryRouter. Static builds default to `/`; set `WEBBLOCKS_STORYBOOK_BASE_PATH=/project/storybook/` for a nested build (PowerShell: `$env:WEBBLOCKS_STORYBOOK_BASE_PATH = "/project/storybook/"`). The root and nested production smoke tests run in both CI workflows before Pages upload. Storybook is published by default under the website’s `storybook/` path; opt out with `storybook.publish: false` in the site configuration.

For the opt-in visual matrix, install the remaining Playwright browsers with `bun run pw:install` and run `bun run test:visual`. The visual project does not yet contain screenshot tests.

## Deployment profiles

| Profile | Build | Preview | Default base |
|---|---|---|---|
| Local | `bun run build` | `bun run preview` | `/` |
| GitHub Pages | `bun run build:pages` | `bun run preview:pages` | Derived from `GITHUB_REPOSITORY` |
| Docker | `bun run build:docker` | `bun run preview:docker` | `/` |

Copy `.env.github-pages.example` to `.env.github-pages.local` and set `GITHUB_REPOSITORY` to the target `owner/repository`. This works on macOS, Linux and Windows without platform-specific shell syntax. For Pages-mode development, run `bun run dev:pages`. Use the same profile and base path for building and previewing; Vite preview is not a strict GitHub Pages server.

To test deployment configuration and actual Vite fixture builds:

```sh
bun run test:baseline
bun run test:deployment
```

### Repository configuration

Edit `webblocks.config.json` to set the public document title, description, language, repository owner/name, deployment defaults and editor/character/effect/animation switches. The neutral defaults preserve current behavior. `siteId: auto` derives a stable identity from the configured repository or `GITHUB_REPOSITORY`; set an explicit unique ID when repository metadata is unavailable or when a repo rename must not change the identity. A Pages build without repository metadata must specify an explicit ID.

Named build commands override the configured target. An explicit `WEBBLOCKS_BASE_PATH` overrides the target's configured base; an alternate JSON can be selected via `WEBBLOCKS_CONFIG_FILE`. Restart Vite after config edits. With a configured owner/name and an automatic base, `bun run build:pages` needs no additional `.env` file for a standard repository deployment. The JSON is public build configuration, not a place for secrets or GitHub tokens.

`editor.enabled: false` hides the existing editor without deleting saved data. Feature flags control the active site character rendering, Character Sheet, falling squares and animation controls. Site metadata does not replace the existing sample page content. Browser-local editor data is isolated by the resolved site ID.

### Site-scoped persistence

Saved editor preferences and committed character rosters use `persist:webblocks:<siteId>:v1` in browser local storage. Use a unique site ID for each independent website. A stable explicit ID can preserve local settings when a repository is renamed, provided its origin stays the same. Browser storage is origin-scoped: a custom domain or protocol change will not transfer data automatically. Namespacing prevents accidental collisions, not access by other scripts on the same origin.

The **Persist Characters** checkbox turns saving on or off immediately. Disabling it removes this site's saved data and saves only an opt-out marker; current in-memory edits remain usable until refresh. Enabling it saves the current roster and preferences. **Reset Character Sheet** restores the default roster and clears the selected character; **Clear Character Sheet** asks for confirmation, removes this site's record (or retains its opt-out marker), and restores defaults immediately. Other sites are untouched. A later durable change can save again when enabled.

Old `persist:root` data is never automatically imported or removed because it has no reliable site ownership. If the old record is valid, **Import Legacy Character Sheet** appears in the editor menu. With persistence enabled, confirm only if the data belongs to this website; it replaces this site's saved roster and preferences, leaving the legacy record unchanged. Invalid or unsupported scoped data loads defaults and is retained until explicit clear, opt-out, or confirmed import. Storage errors show a warning in the editor. Uncommitted drafts, runtime timers, playback and navigation are not restored. Same-site concurrent tabs are last-writer-wins; storage is not a cross-tab synchronization system.

```sh
bun run test:persistence
bun run test:unit
bun run pw:install chromium firefox webkit
bun run test:persistence-browser
```

### Portable website presets

In **Editor Panel > settings > Menu**, select **Export Website Configuration** to download committed character rosters and animation settings as `webblocks.defaults.json`. **Import Website Configuration** validates a same-site file and asks for confirmation before replacing the current roster/settings and draft. Saving opt-out is preserved; if disabled, imported changes are session-only. No browser action publishes the site.

To publish the preset, configure a stable repository/site identity, export the file and review it for public content. Place it alongside `webblocks.config.json` (or the alternate selected config file), commit it, and rebuild. The optional preset is validated and embedded at build time; a wrong identity or invalid file fails the build. Existing valid saved browser edits take precedence. Reset restores the published roster; Clear restores published roster and settings. Without a preset, the framework's original defaults apply. Restart Vite after editing the file. Published configuration is public; do not include secrets.

```sh
bun run test:editor-config
bun run test:unit
bun run test:deployment
bun run test:persistence-browser
```

### Application routes

Pages uses hash routes (for example, `https://owner.github.io/project/#/apps/application`). The repository path belongs to the document URL, not the hash. Local development and Docker retain clean browser routes (`/apps/application`); the supplied Dockerfile installs an NGINX SPA fallback. A locally configured non-root base is also supported when the host serves the SPA beneath that base. Unknown application routes show a recovery page. Legacy route names redirect to canonical paths without discarding route query strings or fragments.

A Pages URL without the hash, such as `/project/apps/application`, is **not** supported on strict static hosting. The compatibility aliases work inside the hash on Pages and as clean paths on local/NGINX hosts. No custom Pages `404.html` redirect is included. GitHub Pages publishing uses the production Actions workflow after repository setup.

Use `routes` from `src/routing/routes.mjs` for internal router links. Do not prepend the deployment base or `#` yourself. Storybook uses its MemoryRouter decorator.

```sh
bun run test:baseline
bun run pw:install chromium firefox webkit
bun run test:routing
# Optional, requires a native NGINX executable on PATH (or NGINX_BIN):
bun run test:nginx
```

### Public assets

For files in `public/`, use `assetUrl('characters/example.png')` from `src/utilities/assetUrl.ts` with an unprefixed path. Vite handles imported source assets and relative stylesheet URLs; do not wrap those in `assetUrl`. WebFall image variants accept unprefixed public paths and explicit external media URLs.

The artwork inventory (manifest and editable SVG sources under [docs/artwork](docs/artwork/)) records replacement assets for asset and license validation. Keep the inventory and licensing notices accurate when changing artwork.

## Strict static Pages verification

Run `bun run test:baseline` for dependency-free verification of the static host and artifact inspector. With dependencies and Chromium installed (`bun run pw:install chromium firefox webkit`), `bun run test:static` builds and qualifies four Pages hosting scenarios without any server-side SPA fallback.

To qualify the exact compiled output before uploading it, build with `bun run build:pages --manifest` and run `bun run verify:static --base /webblocks/ --require-manifest` (replace `/webblocks/` with your actual base path, or `/` for a root site). A failed verification exits nonzero; machine-readable reports are stored under `test-results/`. The optional `--artifact-only` flag skips browser verification and is not a full deployment qualification.

## GitHub Actions CI

The `.github/workflows/ci.yml` workflow validates pushes, pull requests and manual runs using Bun 1.4.5 and the frozen Bun lockfile, TypeScript, lint, unit tests, Vite deployment tests, Chromium routing/persistence tests, and the static Pages matrix. It builds the local and Docker profiles, then qualifies the actual repository Pages build. No website is published by this workflow.

```sh
bun run build:pages --manifest
bun run assemble:pages
bun run security:legal
bun run security:artifact
bun run verify:pages
bun run verify:browsers
bun scripts/assert-pages-artifact.mjs --require-cross-browser
```

`verify:pages` derives the base from the same Vite Pages configuration as the build, requires the manifest, and runs browser verification. Use the same configuration throughout the sequence. The assembly step is required before full qualification. In GitHub Actions, inspect the **Webblocks validation** job; successful runs retain the compiled Pages artifact, and failed runs retain available diagnostic reports. After the first successful run, require this check in the repository's branch protection rules if desired.

## Automated GitHub Pages publishing

Enable **GitHub Actions** as the publishing source in Settings > Pages for each repository. Restrict the `github-pages` environment to the protected default branch, then run **Webblocks Pages** from that branch in the Actions tab. Future default-branch pushes trigger the same production workflow. Configure any custom domain in GitHub Pages settings. No personal access token or separate publishing branch is required.

The production workflow reads GitHub's actual Pages base URL/path, repeats the CI gates, qualifies the compiled website in Chromium, Firefox and WebKit, compares its SHA-256 inventory with the qualification report, then publishes the exact uploaded artifact from a separate job. Validation jobs remain read-only.

### Combined application and Storybook publishing

The default site configuration includes `"storybook": { "publish": true }`. Set `publish` to `false` to publish only the application. The CI component and standalone Storybook validation gates remain mandatory regardless of this flag.

For a repository website at `/project/`, the documentation is at `/project/storybook/`; for a root or custom-domain site it is at `/storybook/`. Open `storybook/?path=/story/characters-artwork--orientations` relative to the website root for a direct story link. The final slash in the Storybook directory URL is intentional.

```sh
bun run build:pages --manifest
bun run assemble:pages
bun run security:legal
bun run security:artifact
bun run verify:pages
bun run verify:browsers
bun scripts/assert-pages-artifact.mjs --require-cross-browser
```

The assembly command derives the Storybook base path from the same resolved Pages configuration as the application. It builds outside `dist/`, reserves `dist/storybook/` (including case variants), and rejects collisions instead of overwriting existing assets. To reassemble or change the publishing flag, start with a fresh Pages build. Qualification serves the entire assembled directory, checks both entry points and all eight Storybook stories, and records the combined file inventory. The workflow uploads only after the final integrity check. No new GitHub permissions or repository settings are required.

### Repository-specific page content

Edit `site/content.json` to customize visible homepage text, application details,
privacy/contact text, software-library content, navigation labels/order and enabled
page templates. The optional file is loaded next to the selected repository config;
partial overrides inherit the original demo content. Place project images under
`public/` and use unprefixed image paths in the content file. Keep document metadata
in `webblocks.config.json` and published character settings in the optional
`webblocks.defaults.json`.
Use `bun run verify:pages` to qualify customized production output.

## Adopt Webblocks in another repository

Use this repository as a GitHub template, then initialize the fresh clone with `bun run init:site init --owner OWNER --repo REPO --title "Project name"`. Alternatively, generate a complete starter into a new directory with `bun run init:site create --destination ../project --owner OWNER --repo REPO`. Both paths preserve the framework and workflows; the copy path refuses all file collisions. By default the starter enables only the homepage and uses an empty character roster; Storybook publication and the editor remain enabled.

### Reusable workflows and nested websites

CI and Pages share `.github/workflows/reusable-build.yml`; the reusable production workflow reads the caller's Pages configuration and publishes only the qualified artifact. Existing root installations require no path changes. To host a Webblocks site inside an existing software repository, generate the starter into e.g. `website/`, keep its complete framework snapshot, install the caller workflows at the repository root, and set `WEBBLOCKS_WORKING_DIRECTORY=website` as an Actions repository variable (or set `working_directory` explicitly). The source path does not change the public Pages URL. Cross-repository callers can use a full commit SHA for the centrally hosted reusable workflows. Update branch protection to the new nested CI check name after the first run, if needed.

### Versioned Webblocks package

Build an npm-installable local package and its integrity manifest with `bun run pack:framework`. The local framework package is `@webblocks/webblocks@0.1.6` (source-first React/Vite API plus full website starter). Install the exact generated `.tgz`, not an unverified registry package of the same name. See [package consumer instructions](packaging/README.md). Run `bun run test:package` for the package contract (registry metadata may be fetched when not cached) and `bun run test:package-consumer` after installing dependencies and Chromium. The package has not been published.

### Multi-repository qualification

`bun run test:multi-repository` generates three independent sites from an actual
packed framework, installs their locked dependencies, builds and qualifies each
Pages artifact, then exercises their storage and assets on one shared origin.
The baseline suite also tests package-generated configurations and safe staged
regeneration without application dependencies.

## Security and licensing

Run `bun run security:inventory`, `bun run security:sbom`, and `bun run security:audit` to inspect dependencies. The production qualification collects third-party and font notices, scans public artifacts, and requires an immutable public corresponding-source link for publication. Do not redistribute packages containing ST-SimpleSquare without permission. Production publishing from private repositories is blocked pending a reviewed corresponding-source arrangement.

## Cross-browser qualification

The reusable CI and Pages workflows qualify the exact compiled artifact in Chromium, Firefox and WebKit at desktop and touch-enabled mobile-sized viewports. After `bun run verify:pages`, run `bun run verify:browsers` followed by `bun scripts/assert-pages-artifact.mjs --require-cross-browser`. Both commands are required for release qualification. The `test:all` command covers source and fixture suites, not this final artifact gate.

## Release packaging

Run `bun run release:pack` and `bun run release:verify` for a versioned source archive, npm tarball and checksums in a fresh `release-dist/` directory. The manifest explicitly identifies the output as a candidate, not production-approved. Run `bun run test:release` for release packaging regression tests. No automated registry publishing or GitHub release is performed.
